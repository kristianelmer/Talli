## Exact fresh-preview defect and smallest decisive regression

Confirmed by source inspection, not an executed reproduction during the gate:

1. `renderRf1086Preview` emits `filing: "aksjonærregisteroppgaven"` (`apps/web/app/lib/rf1086.ts:329,336`). Both Python and TS presentation tests assert that Norwegian label.
2. `generateRf1086Preview` persists `filing: rendered.filing` unchanged (`apps/web/app/actions.ts:1289–1302`).
3. `approveProductionFiling` loads that row, requires owner step-up, builds a manifest with canonical ASCII `obligation: "aksjonaerregisteroppgaven"`, and passes the original preview UUID to SQL (`:5351–5394`).
4. `approve_production_filing` first validates fresh current owner and exact active company/user/year/profile entitlement, then rejects `v_preview.filing <> 'aksjonaerregisteroppgaven'` at SQL line334 with `production_approval_manifest_invalid`. Thus a real ready renderer output is rejected despite a canonical manifest; manually seeded ASCII fixtures bypass the mismatch.

Implement the first regression as a **real disposable-PostgreSQL approval test**, reusing the bounded identity/cleanup patterns in `test_rf1086_database_runtime.py` but never its preinserted approval. A new dedicated fresh-approval fixture is preferable to weakening the historical fixture:

- Use exact owner/company/year, accepted membership, fresh authenticated AAL2/TOTP claims, and exact active Billing-owned RF2025 no-activity pilot with accepted System User binding. Use shipped authorization and granted runtime roles; do not grant broad new SQL rights or set fake paid flags. No provider is required to create an approval.
- Construct the existing no-activity financial/shareholder shape with actual fixture company/setup/shareholder UUIDs, then invoke `renderRf1086Preview(buildNoActivityRf1086Case(company, setup, shareholders))`, exactly as the current action does. This preserves UUID child keys needed by the production adapter; do not feed the CLI-only literal shareholder key `owner` into a fresh-send fixture. Persist the output unchanged, including the Norwegian filing value, real XML and child keys. Build the manifest through the retained production builder with the actual IDs and original hash function, not a hardcoded hash.
- Call the actual current approval RPC in the owner-authorized session. **Current characterization expectation:** `production_approval_manifest_invalid`; zero new approvals/submissions/events. A successful ASCII-control preview in the same otherwise valid setup isolates the cause from MFA, entitlement or RLS failure. The control uses a separate test row/manifest; never rewrite a historical production preview.
- For the #151 successor regression, the same genuine fresh ready preview should yield its authorized approval through the new generated API, with canonical obligation identity kept distinct from Norwegian presentation. Verify original rendered XML bytes, preview identity and all hash inputs remain unchanged. The correct design belongs to the new owner contract; do not globally transliterate historical payload fields or repair history by updating rows.
- Retain paired denial checks for wrong company/owner/year, missing owner confirmation, stale/non-AAL2 claims, missing/suspended/expired pilot and changed payload/manifest. Approval success alone is not send authorization: the existing separate send/release/readiness/authority/restore/signoff checks still run. Do not add gates to the approval stage that previously belonged to send, or remove send gates to make this regression pass.

The minimal test joins the real renderer result to the actual approval boundary. Another pure-string mapping unit test, schema regex, preseeded approval or historical reconciliation-only browser would miss the bug again. Keep one explicitly documented current-behavior characterization if useful, then require successor behavior in the migration acceptance suite rather than encoding the bug as the desired permanent result.
