# Consequential RF freshness: current write/lock inventory

Initial source inspection on 2026-09-24. This is an implementation inventory, not concurrency or production acceptance evidence. The update below distinguishes implemented foundations from the remaining shared admission work. No database/provider calls were made. Scope: source-backed approval and the durable first-send claim; recovery of a claimed operation remains governed by the existing journal.

Other owners and production approval/send remain outside that guarantee.
- Documents now retains verified immutable original bytes and exposes transaction-bound receipt read/assert contracts. See [immutable-document-originals-20260924.json](immutable-document-originals-20260924.json). The original-byte section below explains the gap this foundation addresses. Consequential admission still needs to consume those receipts; archive, backup, expiry and cancellation/deletion integration remain outstanding.
- Governance's customer action now selects a current RF register observation and rereads its receipt. See [customer-register-intake-20260924.json](customer-register-intake-20260924.json). Direct API validation has subsequently been added through the RF and Documents public contracts. These checks still run in separate owner transactions and do not establish shared transaction freshness.

The following initial inventory remains useful for the missing transaction composition, public query grants and writer ordering. It must not be read as a claim that the implemented foundations are still absent.

## Recommended starting point

Reuse the existing **company-wide archive advisory lock** rather than relying on a company-row foreign-key lock. `public.company_archive_lock_company_v1(uuid)` uses `pg_advisory_xact_lock(hashtextextended(company::text, 157))`; `company_archive_lock_scope_v1(company, year)` deliberately takes that same company lock. `company_archive_track_source_write_v1()` already takes it in BEFORE INSERT/UPDATE/DELETE triggers, sorting old/new company IDs. Definitions: `supabase/migrations/20260808120000_company_access_cancellation_lifecycle.sql:76,144,212`.

This is useful coverage, **not a complete freshness barrier**. Missing tables and late acquisition below must be addressed. The lock must cover all company years: a prior-year dividend decision can acquire a current-year reporting date, and cross-year amendments can change reporting evidence. Do not substitute the archive generation for the RF evidence digest; unrelated archive writes change that generation, while some relevant new tables do not currently track it.

## Why company-row / FK locks are insufficient

Holding parent `companies` FOR UPDATE can block FK checks for new children that actually reference it (Governance supported_events, Ledger amendment receipt company FKs are examples). It does not universally serialize existing-child updates, child deletions, permission toggles, or membership changes. It does nothing for RF source/register/preview tables, which only have internal FKs. An ordinary non-key company UPDATE can use a weaker lock compatible with FK KEY SHARE. None of this supplies a shared cross-owner company guard automatically.

## Original-byte retention is a separate missing guarantee

`DocumentsService.verify_document_evidence` (`modules/documents/service.py:191`) explicitly performs external object I/O outside a DB transaction, checks hash/length, rereads metadata and fresh owner, then returns `VerifiedDocumentEvidence`. It documents that a consequential freshness lease is still required. `SupabaseDocumentObjectStorage.read_object` (`adapters/supabase_documents.py:117`) GETs mutable bucket/key and returns content/type only. No object version/generation/ETag is retained or requested. `create_upload_transfer` sends an empty signed-upload request; repository code alone is not proof of version immutability. Direct authenticated storage policies are removed by Documents capability migration, but service-role access still exists.

Current RF `content_version_sha256` is the same observed content hash, not an independently pinned storage generation. SQL retention protects metadata/references and normal application deletion; it does not prevent a bucket object from changing after bytes were checked. Avoid claiming the SQL guard closes this gap.

Minimal self-contained option: add a **Documents-owned immutable retained-original receipt and content record** (bounded by current 10 MiB upload limit), produced from verified bytes before RF transaction, with immutable content/hash/length and narrow public assertion/read contracts. Admission can then pin that retained receipt without network I/O. An immutable/version-addressed object-store implementation is also possible, but must prove the actual provider write/version rules and pin a version in the public receipt; do not infer them from the hash. Old source records can acquire a new verified retention receipt without rewriting old source evidence.

## Minimal admission ordering and tests

1. Authenticate and perform required private original reads outside SQL; resolve owner-owned immutable retention receipt. Obtain necessary provider token binding outside the transaction as existing workflow does. Neither action grants send permission.
2. Start one short **READ COMMITTED** authenticated admission transaction. Acquire company archive guard before any source/decision/document/preview row lock, then RF company/year advisory lock. For multiple companies use sorted IDs; for documents use sorted IDs. Recheck accepted owner, fresh MFA, confirmed AS identity, company-year policy and approved submitter *after* the guard.
3. On that connection, invoke owner public projections for complete Governance enumeration and Ledger amendments, current source/register/preview, Documents retained receipt/metadata, review blockers/overrides/permission. Apply existing public policy/digest functions; compare exact approved manifest/source/preview. Add narrow ACLs, not role switching across unrestricted owner roles.
4. Append immutable approval or consume approval into the existing unique durable submission/journal claim before releasing guard. Commit before provider POST. A new source correction cannot create a second submission after ambiguous/accepted work; recover the original claimed journal. Recheck external entitlement/authority through their existing owner lock contracts as part of send (outside this inventory's owner scope).
5. Never open REPEATABLE READ/SERIALIZABLE and establish its snapshot while waiting for the company lock, then assume reads after acquisition see the preceding writer. Use READ COMMITTED under complete writer exclusion, or explicitly prove an alternative snapshot protocol. Existing independent SERIALIZABLE Governance reads alone do not close RF admission race.
6. Required concurrent tests: guard-wait then committed rename/revocation/eligibility change; previously empty year gains cross-year dividend; finalize/reject/supersede during admission; Ledger correction/reversal; original removal/metadata drift; source/register supersession; new hard-block review/override and permission disable. Each must serialize to correct fresh decision or conflict without submission claim. Also test lock-order races (document removal vs source capture, acknowledgement vs approval), immutable retained-byte receipt against storage replacement, replay and unknown-provider outcome without repeat POST. Run under actual owned DB executor roles and both migration topologies.
