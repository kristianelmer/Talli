# RF unknown-outcome recovery research — 2026-09-30

The provider documents recovery through identical-body, same-key POST replay. It does **not** document an operation-by-key GET, an unlimited replay lifetime, or enough detail to establish confirmation replay safety independently of the general prose. Keep uncertain operations quarantined until the applicable recovery contract is established. No credentials, provider business endpoints, or production changes were used for this research; only public documentation was fetched.

## Primary evidence

- Skatteetaten's [RF documentation, pinned at `f57ad249`](https://github.com/Skatteetaten/api-dokumentasjon/blob/f57ad2492a12dac282cb7b36f6570ff85de2a1e7/docs/api/innrapportering-aksjonaerregisteroppgave.md#parameter-idempotencykey) requires unique UUID keys. Identical request bodies and keys return the same response; only the first request is processed. Missing feedback is the stated use case. No retention duration, expiry behavior, deduplication namespace, concurrent-request behavior, or failed-response caching policy is specified.
- The same document's error tables define `GLD_019` / HTTP 409 as a previously used key, without explaining how that relates to identical replay. `GLD_1029` concerns sending an underskjema after confirmation. `GLD_1016` can mean missing main form **or** wrong taxpayer/year. Prefill can fall back to the preceding year. These are not proofs that an uncertain operation did not execute. [RF errors and prefill](https://github.com/Skatteetaten/api-dokumentasjon/blob/f57ad2492a12dac282cb7b36f6570ff85de2a1e7/docs/api/innrapportering-aksjonaerregisteroppgave.md)
- [SwaggerHub's registry](https://api.swaggerhub.com/apis/skatteetaten/innrapportering-aksjonaerregister-api) reports default version **1.2.0**, published 2026-08-25; no later version is listed. Its [OpenAPI](https://api.swaggerhub.com/apis/skatteetaten/innrapportering-aksjonaerregister-api/1.2.0) declares required `idempotencyKey` headers for `1086H` and `1086U`, but **omits the header from `bekreft`**, including inherited parameters. That is an unresolved contract discrepancy, not evidence that confirmation ignores the header.

| Lost response | Documented result / discovery | Engineering conclusion |

| Main `POST /{year}/1086H` | Returns `hovedskjemaId`; key header explicit. | Exact replay has documentary support; no key-to-main GET is exposed. Delayed replay lifetime remains unspecified. |

| `POST /{year}/{main}/bekreft?antall_underskjema=…` | Returns delivery reference, dialog ID and transmission ID; key header absent from operation specification. | Resolve the discrepancy before enabling uncertain confirmation replay. Do not invent IDs from the main UUID. |

The [OpenAPI](https://api.swaggerhub.com/apis/skatteetaten/innrapportering-aksjonaerregister-api/1.2.0) exposes three GETs: document list by transmission ID, document by transmission/document IDs, and prefill by company/year. None is an operation-status lookup by key or main ID. Successful document retrieval can supply positive evidence once a transmission is reliably identified; unavailable documents cannot establish nonexecution.

[Dialogporten search](https://docs.altinn.studio/en/dialogporten/user-guides/searching-for-dialogs/) supports party/service filters and continuation-token pagination; results depend on authorization. [Reference lookup](https://docs.altinn.studio/en/dialogporten/user-guides/looking-up-dialogs/) accepts Altinn instance, correspondence or dialog identifiers, not an RF idempotency key. [Transmissions](https://docs.altinn.studio/en/dialogporten/reference/entities/transmission/) are immutable, may link to another transmission, and can be excluded by authorization. **Inference:** discovery can produce candidates for read-only investigation, but missing results, a matching company/year, or matching XML alone cannot identify one particular logical submission among duplicates. No inspected RF contract promises a mapping from its operation key/main ID into searchable Dialogporten metadata.

## Implementation seams and unresolved requirements

At Talli revision `746c3c29`, `source_dispatch.py:assess` and `_DurableJournal.prepare` deliberately stop prepared/unknown mutations. `ShareholderRegisterSourceDispatchWorkflow.send` never converts them into new grants. `rf1086_authority.py` already preserves UTF-8 body bytes and sends keys on all three POSTs. Its GET adapter and `rf1086_dialogporten.py` start from retained confirmation references; they do not discover lost confirmations.

A future explicit recovery command should retain original environment, method, path/query, company/year, authority connection identity, exact bytes/hash and key; recheck current authorization; append an independently admitted recovery intent; serialize concurrent recovery; and preserve original uncertainty if recovery itself fails. Those are **proposed Talli safeguards**, not documented provider namespace rules. Replacing credentials must not silently change the system user/client context. A valid replay success can then append a resolution and resume at the next operation without rewriting history. An error or malformed response must not mint success, nonexecution, or a fresh key.

Provider clarification/conformance still needed: key retention and expiry behavior; whether client/system-user/company/environment/path/query participate in deduplication; identical replay versus `GLD_019`; partial failure/concurrency behavior; and explicit `bekreft` replay semantics. No inspected source supplies a safe numeric retry window. These gaps do not require recruiting a production AS to continue software work, but synthetic tests cannot establish the missing provider guarantees.
