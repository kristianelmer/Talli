## Concrete drift and limits

1. **Lookup loses the requested reference.** `querySystemUser` accepts `externalRef` and requires it in the response, but sends only `system-id` and `orgno`. Current documentation supplies `external-ref` specifically to distinguish several users for the same customer/system. The migration must preserve exact identity selection, rather than rely on an unspecified lookup choice. [Code](https://github.com/kristianelmer/Talli/blob/b30312de11ad942479421def243e4a2252fbf166/apps/web/app/lib/system-user-authority-client.ts#L518), [official query](https://docs.altinn.studio/en/authorization/guides/system-vendor/system-user/byquery/).
2. **Documented lookup responses are rejected.** The parser requires exactly six keys. Altinn's documented response also contains `integrationTitle`, `productName`, `created`, `supplierName`, and `supplierOrgno`. Thus that documented response fails the current parser before preflight; existing tests explicitly lock in extra-field rejection. This is a confirmed code/document mismatch, not a newly observed live failure. Preserve strict identity/type/deletion checks when characterizing the real schema. [Parser](https://github.com/kristianelmer/Talli/blob/b30312de11ad942479421def243e4a2252fbf166/apps/web/app/lib/system-user-authority-client.ts#L307), [official response](https://docs.altinn.studio/en/authorization/guides/system-vendor/system-user/byquery/#response-fields).
3. **TT02 confirmation host mismatch.** The allowlist contains `am.ui.at22.altinn.cloud` and `authn.ui.tt02.altinn.no`; the newer guide demonstrates `am.ui.tt02.altinn.no`, which Talli rejects. The older API reference still demonstrates the AT22 host. This is conflicting published host evidence; establish the current approved TT02 origin during authorized conformance rather than allow arbitrary redirects. Production's `am.ui.altinn.no` was not shown to drift. [Allowlist](https://github.com/kristianelmer/Talli/blob/b30312de11ad942479421def243e4a2252fbf166/apps/web/app/lib/system-user-authority-client.ts#L133), [guide](https://docs.altinn.studio/en/authorization/guides/system-vendor/system-user/systemuserrequest/#method-a-vendor-controlled-creation).
4. **Additional grant claim needs verification.** Talli adds `sub=clientId` for System User grants. Neither the generic grant claim table nor the RAR example documents it, and the generic spec warns that undocumented claims may be rejected. No live rejection was tested; historic success must not be overwritten with an invented failure. Resolve this against current authorized conformance before treating that claim as required behavior. [Code](https://github.com/kristianelmer/Talli/blob/b30312de11ad942479421def243e4a2252fbf166/apps/web/app/lib/maskinporten.ts#L218), [grant specification](https://docs.digdir.no/docs/Maskinporten/maskinporten_protocol_jwtgrant.html), [RAR](https://docs.digdir.no/docs/Maskinporten/maskinporten_func_systembruker.html).
5. **Documentation drift, no immediate lifetime defect.** The current JWT specification says maximum **180 seconds**, recommended 120; the [consumer guide](https://docs.digdir.no/docs/Maskinporten/maskinporten_guide_apikonsument) still says maximum 120. Talli's 119 seconds satisfies both. No lifetime increase is required by this research.
6. **Request-shape/status compatibility remains unproven.** The older response model documents `created`, while Talli requires an exact eight-key request response. The API list example spells timeout `Timedout`, whereas Talli accepts `TimedOut` or lowercase `timedout`. These require exact-response characterization; list examples alone do not prove the individual-request endpoint emits that shape/case. [Model](https://docs.altinn.studio/en/api/authentication/systemuserapi/systemuserrequest/external/model/), [API](https://docs.altinn.studio/en/api/authentication/systemuserapi/systemuserrequest/external/), [parser/status map](https://github.com/kristianelmer/Talli/blob/b30312de11ad942479421def243e4a2252fbf166/apps/web/app/lib/system-user-authority-client.ts#L138).

## Prerequisites not exercised

Official [onboarding](https://docs.altinn.studio/en/authorization/getting-started/systemuser/) (modified **17 July 2026**) requires the vendor's Norwegian organization, relevant terms/onboarding, a registered Maskinporten client/key and granted System User scopes. The registered system must bind that client, required resources and exact redirect URI. The customer must approve the rights for its own organization; control-plane scopes do not supply the service owner's separate RF-1086 scope or filing authority.

The existing production configuration names `TALLI_PROD_MASKINPORTEN_CLIENT_ID`, `TALLI_PROD_MASKINPORTEN_KEY_ID` and `TALLI_PROD_MASKINPORTEN_PRIVATE_KEY_PEM`. No values were read. Current key validity, scope grants, registered-system definition, approval/relationship state, callback reachability and service-owner access remain unverified here. Repository July evidence is historical, not a fresh credential or connection verdict. Keep test/production separation; Digdir expressly disallows production certificates in test.

A later authorized conformance run must use the owner-designated environment/company and preserve the existing action-time controls. This research does not authorize obtaining credentials, creating requests, registering/updating systems, delegating rights, testing real filing, promoting production or adding client-agent access.
